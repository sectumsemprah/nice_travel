# 旅行攻略与旅行记忆项目方案

## 背景与动机

用户希望构建一个辅助制定旅行攻略、留下旅行记忆的项目，并将其发布到 GitHub。项目核心价值是把分散在社交平台、地图、个人偏好和旅行素材中的信息组织起来，生成可执行的个性化行程，并在旅行结束后沉淀为路径图、电子相册等记忆资产。

当前仓库缺少 `openspec/project.md`、`AGENTS.md` 与 `openspec/specs/**/spec.md`，因此本提案同时承担项目级上下文补齐建议的作用。在这些基础约定未确认前，本变更停留在 Review & Align 阶段，不进入代码实现。

## 目标与范围

本次目标是设计一版可落地的项目方案，明确产品边界、架构分层、核心模块、数据模型、合规安全、GitHub 开源形态与分阶段任务。

本次范围包含：

- 根据用户目的地、时间、预算、同行人、兴趣偏好、节奏偏好等条件生成个性化旅行行程。
- 支持从社交平台旅行信息中检索、整理、筛选候选内容，但必须遵守平台条款、robots.txt、公开 API 或用户授权导入边界。
- 支持将景点、餐饮、住宿、交通节点组织成多日行程，并生成路径图。
- 支持用户上传或选择旅行照片、文字、地点轨迹，生成电子相册或旅行回忆页。
- 支持账号、项目空间、行程版本、导出分享等基础能力。
- 支持以 GitHub 仓库形式开源，包含 README、许可证、贡献规范、环境变量示例、部署说明和基础 CI。

## 非目标

- 不直接绕过社交平台反爬、登录限制、版权限制或 API 额度限制。
- 不承诺覆盖所有国家/地区地图服务，首版默认聚焦中国大陆用户常见场景，并保留适配国际地图服务的接口。
- 不在首版实现复杂商业化、多人实时协同编辑、供应链下单、酒店/机票交易闭环。
- 不在本提案阶段输出生产代码或执行实现任务。

## 用户故事与典型场景

### 场景 1：出发前制定攻略

用户输入“上海出发，五一去成都 4 天 3 晚，预算中等，喜欢美食、城市漫步、轻松节奏”。系统检索公开旅行信息与内置地点数据，提取高频推荐、避坑提示、开放时间、交通耗时等信息，生成按天组织的行程，并允许用户调整节奏和偏好。

### 场景 2：旅行中动态调整

用户发现某景点天气不佳或排队过长，系统基于当前位置、剩余时间、兴趣偏好和营业状态推荐替代路线，并保留行程版本。

### 场景 3：旅行后生成回忆

用户上传照片和短文字，系统按时间、地点和主题生成旅行路径图、图文电子相册、回忆摘要，并支持导出为网页、图片集或 PDF。

## 主要方案

### 产品定位

项目定位为“旅行攻略智能工作台 + 旅行记忆生成器”。首版建议做成 Web 应用，优先服务个人用户制定攻略、管理行程、沉淀回忆。GitHub 开源形态建议采用“应用代码 + OpenSpec 规范 + 示例数据 + 可选部署模板”。

### 建议技术栈

在未确认项目偏好的情况下，默认建议：

- 前端：Next.js + TypeScript + React + Tailwind CSS。
- 后端：Next.js Route Handlers 或独立 NestJS/FastAPI。首版为降低部署复杂度，建议先使用 Next.js 全栈结构。
- 数据库：PostgreSQL + Prisma。
- 缓存与任务队列：Redis + BullMQ，首版可选；若只做 MVP，可先用数据库任务表替代。
- 对象存储：S3 兼容服务，用于照片、相册封面、导出文件。
- 地图：高德地图/百度地图/Mapbox 之一，通过 Provider 接口隔离。
- AI 能力：可插拔 LLM Provider，用于内容摘要、偏好匹配、行程生成、相册文案生成。
- 检索：优先公开 API、RSS、用户授权导入、手动链接解析；搜索索引可使用 PostgreSQL full-text 起步，后续升级到 Meilisearch/Elasticsearch。
- 部署：Vercel/Railway/Fly.io + Supabase/Neon/Postgres，或 Docker Compose 自部署。
- CI：GitHub Actions 执行 lint、type-check、test、build。

### 架构分层

建议采用清晰分层：

- `presentation`：页面、组件、交互状态、表单校验。
- `application`：用例编排，例如“生成行程”“刷新候选内容”“生成相册”。
- `domain`：旅行计划、地点、偏好、行程约束、回忆资产等核心模型。
- `infrastructure`：数据库、地图服务、LLM、对象存储、社交信息源适配器。
- `jobs`：异步任务，例如检索、摘要、路线计算、相册导出。
- `observability`：结构化日志、指标、任务状态、错误追踪。

### 对外接口

首版建议提供以下 API 能力：

- `POST /api/trips`：创建旅行项目。
- `GET /api/trips/:id`：获取旅行项目详情。
- `POST /api/trips/:id/sources/search`：根据目的地和偏好检索候选旅行信息。
- `POST /api/trips/:id/itinerary/generate`：生成个性化行程。
- `PATCH /api/trips/:id/itinerary`：编辑行程。
- `POST /api/trips/:id/routes/render`：生成路径图。
- `POST /api/trips/:id/memories/assets`：上传照片或素材。
- `POST /api/trips/:id/memories/generate`：生成电子相册或旅行回忆页。
- `GET /api/exports/:id`：查询导出结果。

### 核心数据模型

建议建模：

- `User`：用户身份、偏好默认值、授权信息。
- `Trip`：目的地、日期、预算、同行人、状态、版本。
- `PreferenceProfile`：兴趣标签、节奏、饮食、交通、禁忌、无障碍要求。
- `TravelSource`：来源平台、URL、授权方式、抓取/导入状态、版权标记。
- `TravelInsight`：从来源中提取出的地点、建议、风险、热度、置信度。
- `Place`：地点基础信息、坐标、营业时间、标签、来源引用。
- `ItineraryDay` / `ItineraryItem`：每日行程与节点。
- `RouteSnapshot`：路径点、距离、时间、地图 Provider、渲染产物。
- `MemoryAsset`：照片、视频、文字、位置、时间、元数据。
- `MemoryAlbum`：相册结构、主题、文案、导出格式。
- `Job`：异步任务状态、错误信息、重试次数、traceId。

### 关键流程

1. 用户创建旅行项目并填写偏好。
2. 系统根据目的地和偏好检索或导入候选内容。
3. 系统抽取地点、建议、限制、风险与来源引用。
4. 系统按时间、交通、预算、兴趣匹配度生成候选行程。
5. 用户编辑确认行程，系统生成路径图。
6. 旅行中用户可记录照片、文字、轨迹与地点。
7. 旅行后系统生成电子相册、回忆页和可导出文件。

### 安全、权限与隐私

- 默认只处理公开内容、用户主动提供的链接、用户授权导入的数据。
- 存储来源 URL、摘录摘要和引用，不复制大段原文或未授权图片。
- 用户照片、轨迹、偏好属于敏感个人数据，默认私有。
- 分享链接必须有访问令牌、过期时间或撤销能力。
- API 必须进行鉴权、资源归属校验、输入校验和速率限制。
- LLM 调用前应最小化发送个人敏感字段，并记录可审计的调用用途。

### 性能与容量

- 检索、摘要、路线计算、相册导出默认异步化。
- 任务必须有状态机、有限重试、失败原因和用户可见状态。
- 地图、LLM、搜索服务应做 Provider 隔离，支持缓存与降级。
- 首版容量目标建议：单用户 20 个旅行项目、单项目 200 个候选地点、500 张照片以内。

### 可观测性

- 使用结构化日志，包含 requestId、userId、tripId、jobId、traceId、耗时、结果状态。
- 记录关键指标：生成成功率、任务耗时、外部 API 错误率、导出失败率。
- 对 LLM/地图/搜索外部依赖设置错误分类，便于定位是用户输入、额度、网络还是 Provider 故障。

### 兼容性与回滚

- 首版不要求兼容旧数据，但数据库迁移必须可回滚。
- 社交平台信息源、地图服务、LLM 服务都通过接口隔离，便于替换。
- 生成类产物保存版本，用户可回到上一个行程或相册版本。
- GitHub 开源仓库不提交真实密钥、个人数据、受版权保护的样例素材。

## TREK 参考分析

参考项目：[sectumsemprah/TREK](https://github.com/sectumsemprah/TREK)。本次分析基于 TREK 当前源码结构与 README，TREK 是一个自托管、实时协作的旅行规划套件，覆盖地图、预算、清单、行程、文件、旅行日志、PWA、认证与 MCP 等能力。

### 适合直接参考的部分

- Monorepo 结构：TREK 使用 `client`、`server`、`shared` 三工作区组织前端、后端和共享契约。我们的项目也适合采用类似的 `apps/web`、`packages/domain`、`packages/providers`、`packages/shared` 分层。
- 共享契约：TREK 将 API schema 与类型放在 `shared` 包中，前后端共享校验与类型。我们的项目应参考此思路，把 Trip、Place、Itinerary、MemoryAlbum、Job 等契约统一维护。
- 旅行计划核心模型：TREK 的 `trips`、`days`、`places`、`day_assignments` 模型适合作为行程编排的参考基础。
- 地图与地点能力：TREK 的地图模块支持 OSM/Nominatim、Overpass、Google Places、地图链接解析、地点照片缓存和地图 Provider 降级。我们的项目可参考其 Provider 隔离、缓存和错误处理方式。
- 文件与照片管理：TREK 的 Journey/Photos 模块可参考其本地上传、缩略图、素材关联、权限校验和照片 Provider 抽象。
- 旅行记忆模型：TREK 的 Journey 设计将 Trip 中的地点同步成 Journey skeleton，再由用户补充故事、照片、心情、天气等内容。这个“计划转记忆”的桥接思路非常适合保留。
- 分享与权限：TREK 支持成员、分享链接、只读公开页、访问控制和撤销能力。我们的相册/攻略分享可参考其资源归属与分享令牌设计。
- 安全工程：TREK 对 SSRF、Cookie Secure、API Key 加密、文件上传类型、WebSocket 鉴权和速率限制有较完整处理，应作为安全基线参考。
- 自托管与 GitHub 交付：TREK 的 Dockerfile、docker-compose、README、LICENSE、SECURITY、CONTRIBUTING、CI 与 Helm 目录都值得参考。

### 建议重写或另行设计的部分

- 社交平台旅行信息检索：TREK 主要做地图/列表/文件导入，不是面向小红书、抖音、微博、B站等社交内容的合规检索与洞察筛选。我们的项目需要新增 `TravelSource`、`TravelInsight`、`SourceProvider`、版权/授权状态、证据引用和内容去重能力。
- 个性化攻略生成：TREK 的行程更偏用户手动规划与拖拽编排，不是从偏好、预算、节奏、人群、天气、拥挤度、避坑信息中自动生成候选攻略。我们的项目需要独立的行程生成引擎和约束评分模型。
- AI 编排层：TREK 的 LLM 当前更偏预订文件解析等插件能力。我们的项目需要将 LLM 作为产品主链路，覆盖信息摘要、地点聚类、偏好匹配、行程解释、相册文案和风险提示。
- 中国大陆地图与内容生态：TREK 默认面向国际自托管用户，地图生态以 OSM/Google/Mapbox 为主。我们的项目如果面向中国大陆用户，应抽象高德/百度/腾讯地图 Provider，并处理国内平台链接与地点标准化。
- 数据库选择：TREK 默认 SQLite，适合个人自托管。我们的项目若希望 GitHub 开源后支持云部署、多用户、异步任务和检索，建议首版即使用 PostgreSQL。
- 后端形态：TREK 使用 NestJS + Vite React。我们的首版若追求上手快，可使用 Next.js 全栈；若追求长期复杂后端治理，可选择 NestJS。不能简单照搬 TREK 的后端目录，应按我们的领域边界重新组织。
- 插件/MCP：TREK 的 MCP 和插件系统很强，但首版不是必要主链路。我们的项目可保留 Provider 插拔，不建议一开始照搬完整插件平台。
- 协作套件：TREK 的多人协作、聊天、投票、预算分账很完整，但对首版旅行攻略生成不是核心。建议暂缓，避免产品重心过散。

### 对本项目的吸收结论

本项目应借鉴 TREK 的“工程骨架与旅行管理成熟模块”，但重写“信息检索、洞察提取、个性化生成与记忆叙事”四个核心差异层。更具体地说，TREK 可以作为旅行数据管理和地图交互参考，而本项目的差异化应放在“社交内容到可执行攻略，再到旅行回忆资产”的闭环。

## 风险清单与缓解措施

- 社交平台合规风险：仅使用公开 API、用户授权导入和链接摘要；避免绕过反爬和复制受版权保护内容。
- 行程生成不准确：保留来源引用、置信度、人工编辑能力和“建议而非承诺”的提示。
- 地图 Provider 受限：通过 Provider 接口隔离，支持降级为静态地点列表。
- LLM 成本与延迟：异步任务、缓存、分阶段摘要、限制输入长度。
- 隐私泄露：默认私有、最小化外发、分享链接可撤销、敏感字段脱敏日志。
- 照片存储成本：限制单项目容量，支持压缩、缩略图、对象生命周期策略。
- 开源密钥泄露：使用 `.env.example`、GitHub secret scanning、CI 禁止提交高风险文件。

## 决策记录（Decisions）

- 默认采用 Web 应用优先，而不是移动端优先：便于快速开源、部署和迭代；移动端能力可在后续通过 PWA 或原生 App 扩展。
- 默认采用 Next.js 全栈方案：减少首版仓库复杂度，同时仍可保留清晰领域层和 Provider 边界。
- 默认使用 PostgreSQL：适合结构化旅行数据、任务状态和基础全文检索。
- 默认所有外部信息源必须可追溯：降低版权、准确性和审计风险。
- 默认生成类流程异步化：避免长请求超时，便于重试和状态展示。
- 默认个人照片、轨迹和偏好为私有：符合安全/隐私保守原则。
- 默认关键路径补齐自动化测试：包括行程生成、权限校验、任务状态、导出流程。

## 澄清问题清单

### 阻断级

1. 是否批准先按“Web 开源项目 + Next.js 全栈 + PostgreSQL + 可插拔 Provider”的方向作为项目基线？
2. 目标用户与首发地域是否确认为“中国大陆个人旅行用户”为主？如果不是，地图、平台和合规策略会明显不同。
3. 社交平台信息来源是否限定为“公开 API、用户授权导入、用户粘贴链接/文本”，并明确不做绕过平台限制的爬取？
4. GitHub 开源许可证是否选择 MIT、Apache-2.0 或暂不声明？这会影响仓库初始化文档。

### 非阻断级

1. 是否首版支持账号系统？默认决策：支持最小账号体系，因为旅行项目、照片和分享权限需要资源归属。
2. 是否首版支持 PDF 导出？默认决策：先支持网页相册与图片导出，PDF 作为后续增强，原因是 PDF 版式验证成本较高。
3. 是否首版支持多人协作？默认决策：暂不支持，仅支持分享只读链接，原因是协同编辑会显著增加权限与冲突处理复杂度。
4. 是否首版接入真实支付或商业化？默认决策：不接入，先完成产品闭环与开源基础。
